# Пояснительная записка: Activity Shield

## Пакет 1.0.4 для публичного канала

После загрузки 1.0.3 в AMO подготовлен новый номер 1.0.4 для отправки в публичный канал: AMO проверяет уникальность номера среди всех версий дополнения независимо от канала. Изменены только метаданные версии и номер в интерфейсе; код защиты и белого списка сохранён. Результаты проверок ниже относятся к функционально той же версии 1.0.3. В `PUBLISHING.md` уточнена ссылка **«Изменить»** в блоке размещения версии на первом экране загрузки. Доставка обновлений начнётся после публичной публикации в аккаунте Mozilla; она пока не подтверждена.

## Изменения 1.0.3: совместимость редакторов и белый список

Подмена Selection API может мешать веб-редакторам, в том числе WhatsApp Web. Добавлен белый список доменов: кнопка для текущего сайта, ручное добавление домена/URL и удаление правила. `web.whatsapp.com` включён по умолчанию при создании настроек, но может быть удалён пользователем. Список не передаётся наружу и хранится в `storage.local`.

Статическая инъекция заменена постоянной динамической регистрацией упакованного `shield.js` в MAIN при `document_start`, с `excludeMatches`. На исключённом URL не выполняется ни подмена API, ни фильтрация событий; на других URL сохраняется ранний запуск. Обновление правил подтверждается меню только после успешной регистрации и записи настроек; операции сериализуются. Перезагрузка уже открытого документа обязательна. Каждый фрейм сопоставляется по собственному URL.

Настольные интеграционные проверки изменяют правила через реальный интерфейс установленного расширения, сравнивают нативные и защищённые API, проверяют ввод в contenteditable-редактор, зависящий от Selection API, восстановление защиты после удаления правила и сохранение защиты на другом домене. Отдельно проверяется сохранение правил и регистрации после полного перезапуска Chromium. Доступ к аккаунту WhatsApp и отправка сообщений не требуются: реальный WhatsApp Web после обновления следует проверить пользователю на своей учётной записи.

Для обновлений выбран публичный канал AMO у существующего дополнения с неизменным ID. Сборки и тексты карточки подготовлены, но в аккаунте Mozilla не опубликованы. По правилам Mozilla ранее установленные самораспространяемые XPI без `update_url` могут получить более новую публичную версию того же ID. Отдельная Android-сборка имеет другой ID. Порядок публикации, условия обновления и тексты карточки приведены в `PUBLISHING.md`.

10 ноября 2026 года настольный набор завершился успешно: 10 проверок, включая настоящее меню, добавление/удаление домена, зависимый от Selection API редактор, кнопку текущего домена и перезапуск Chromium. Мобильный прогон версии 1.0.3 на Android 16 / Firefox 159.0.1 также прошёл: фактическая установка динамического скрипта, выделение, долгий тап, ввод, полный экран и переход в другое приложение (Android Settings) с возвратом. Отдельные результаты — `android/verification-1.0.3.json` и `android/verification-1.0.3.png`. Редактирование белого списка через мобильный popup этим прогоном не автоматизировано; общий интерфейс и изменение регистрации проверены на настольных браузерах. Проверка мобильного манифеста — без ошибок, предупреждений и замечаний.

## Постановка задачи

Веб-страницы могут получать сведения о видимости вкладки, фокусе окна, вызове контекстного меню и выделении текста. Требуется ограничить доступ скриптов страниц к этим сведениям в Chromium и Firefox, сохранив возможность пользоваться браузером. Дополнительное условие версии 1.0.2 — обработать требование сайта о полноэкранном режиме.

Результат работы — расширение Manifest V3, независимая демонстрационная страница и интеграционные тесты. Установочные папки и ZIP находятся в `dist/`; подробная инструкция — в `README.md`.

## Дополнение 1.0.2: требование полноэкранного режима

Реализован синтетический Fullscreen API. До запроса `document.fullscreenElement` равен `null`. После `element.requestFullscreen()` сайт получает успешный Promise, читает запрошенный элемент (или внешний host для Shadow DOM) и получает синтетическое `fullscreenchange`. Окно остаётся обычным; расширение не вызывает нативный переход. При явном `document.exitFullscreen()` состояние сбрасывается и отправляется событие выхода. Имеющиеся префиксные webkit/moz-аналоги обработаны; ошибочный запрос на отсоединённом элементе отклоняется.

Нативные события полного экрана и ошибки не передаются сайту. Esc и смена вкладки/приложения не меняют синтетическое состояние. В независимое демо добавлено требование «Начать: требуется полный экран»: обычный код сайта проверяет `fullscreenElement` и разрешает продолжить, не имея доступа к расширению. Информационные панели расширения обновлены.

Проверка в Chromium 156.0.8078.4 и Firefox 159.0.1 выполнена с фактической установкой расширения и контрольным прогоном без него. Настоящий клик в контроле включает `:fullscreen` и порождает доверенное событие; с защитой CSS остаётся обычным, размеры окна сохраняются, событие синтетическое. Проверены успешный Promise, условие допуска на демо, Esc/смена вкладки, явный выход, ошибочный запрос и чтение состояния в Shadow DOM. Все 7 настольных проверок прошли; подробные JSON при повторном запуске сохраняются в `test-results/fullscreen-*.json`.

Повторный полный прогон 1.0.2 на отдельном эмуляторе Android 16 / API 36 с Firefox 159.0.1 также прошёл. В контрольном режиме реальное касание кнопки включило нативный полный экран (`:fullscreen: true`, доверенное событие). В защищённом режиме запрос успешно завершился, `fullscreenElement` был ненулевым, CSS остался обычным, событие входа было синтетическим. После Home/возврата состояние оставалось синтетически полноэкранным, новых событий полного экрана и фокуса не появилось. Дополнительно прошли прежние проверки выделения, долгого нажатия, настоящих кликов и ввода. Результаты этой версии сохранены отдельно: `android/verification-1.0.2.json` и `android/verification-1.0.2.png`; доказательства 1.0.1 сохранены без изменений. Проверка мобильного манифеста завершилась с нулём ошибок, предупреждений и замечаний. Проверка 1.0.2 на физическом телефоне остаётся ручным шагом.

Граница решения: это подмена перечисленных JavaScript API. CSS `:fullscreen`, media queries, геометрия окна/экрана и нативный F11 не подменяются; по ним намеренно противодействующий сайт может определить обычное окно. `isTrusted` синтетических событий остаётся `false`. Виртуальное состояние iframe не переносится в родительский документ. Полноэкранное видео, презентации и игры при включённой защите также остаются в окне. Нельзя утверждать, что пройдены все возможные проверки полноэкранного режима. Нативный контракт и отдельные каналы описаны в [Fullscreen API](https://developer.mozilla.org/en-US/docs/Web/API/Fullscreen_API).

Изменение исходников не обновляет ранее подписанный XPI 1.0.1. Для постоянной установки 1.0.2 требуется отправить новую версию существующего дополнения на подпись Mozilla и установить полученный файл с тем же ID.

## Модель угроз и критерий успеха

Рассматривается обычный скрипт сайта, который после начала загрузки страницы подписывается на DOM-события или опрашивает соответствующие браузерные API. Он не контролирует браузер и операционную систему. До выполнения его кода расширение изменяет наблюдаемые результаты в том же контексте JavaScript.

Критерий успеха: через предусмотренные точки доступа сайт читает «видима, в фокусе, выделения нет» и не получает перечисленные события. Пользователь может переключать вкладки, выделять текст, вызывать стандартное меню и вводить текст. Проверяется именно этот ограниченный критерий. Невозможность обнаружить отсутствие пользователя через любые доступные каналы не заявляется.

## Почему расширение

Код, выполненный вручную в консоли, может запускаться уже после того, как сайт сохранил исходные методы и зарегистрировал обработчики. Обычный изолированный content script также не меняет JavaScript-прототипы, которыми пользуется сайт.

В версиях до 1.0.3 использовался статический `content_scripts`. В 1.0.3 фоновый модуль регистрирует скрипт через `scripting.registerContentScripts` с `runAt: "document_start"`, `world: "MAIN"` и исключениями доменов. После регистрации браузер сам запускает код до обычных скриптов страницы, без обращения к фону на каждой навигации. API описан в [MDN](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/scripting/registerContentScripts); MAIN поддерживается в Firefox с версии 128.

## Реализация

1. На `Document.prototype` геттеры `hidden` и `visibilityState` заменяются на константные значения `false` и `"visible"`, а `hasFocus()` возвращает `true`. При наличии аналогичных `webkit`-свойств они подменяются согласованно.
2. На `window` до обработчиков сайта регистрируются capture-слушатели. Для защищаемых событий вызывается `stopImmediatePropagation()`: событие не доходит до последующих обработчиков и нижележащих узлов. Это охватывает подписки через `addEventListener`, свойства `on…` и inline-обработчики, если расширение успело установиться раньше.
3. `contextmenu` блокируется вместе с мышиными и pointer-событиями, содержащими правую кнопку. Иначе сайт мог бы узнать о ПКМ через `pointerdown`, `mousedown` или движение с зажатой кнопкой. Также блокируются события клавиши контекстного меню и Shift+F10.
4. Для выделения блокируются `selectstart`, `selectionchange` и `select`. Дополнительно маскируется чтение `Selection`: строка, узлы и диапазоны выглядят пустыми. Сохраняются настоящий объект `Selection` и методы изменения выделения. Доступ к `Selection.prototype` сам по себе не обходит подмену, поскольку заменяются методы и свойства прототипа.
5. Для `input` и `textarea` отдельно маскируются свойства `selectionStart`, `selectionEnd` и `selectionDirection`, с сохранением сеттеров. Эти свойства относятся к отдельному механизму выделения, описанному в [Selection API](https://developer.mozilla.org/en-US/docs/Web/API/Selection_API).
6. `blur`/`focus`/`focusin`/`focusout` окна и документа блокируются. В версии 1.0.1 дополнительно фильтруются события активного элемента, порождённые уходом приложения в фон и возвратом. Для этого внутри замыкания сохраняются исходные `hasFocus`, геттеры `hidden` и `activeElement`, а также элемент, потерявший фокус при уходе. Чтение реального состояния не раскрывается странице. Переходы между полями активной страницы сохраняют обработчики форм; `relatedTarget` помогает отличить их от перехода из документа.
7. Динамические `allFrames` и `matchOriginAsFallback` запрашивают применение к подходящим фреймам и связанным документам. Каждый URL сопоставляется с исключениями отдельно; ограничения раннего внедрения остаются.

`preventDefault()` в защите не вызывается: блокируется передача событий JavaScript-коду, а стандартные действия браузера не отменяются. Пользовательский ввод не имитируется. С версии 1.0.2 генерируются только синтетические события явных запросов Fullscreen API; подделка `Event.isTrusted` не выполняется.

В 1.0.3 добавлен фоновый модуль регистрации и локальное хранилище белого списка. В расширении нет сетевых запросов, хранилища истории и внешних зависимостей. Запрашиваются доступ к HTTP(S)-страницам, `scripting` для ранней регистрации и `storage` для списка. Сборка Firefox отдельно декларирует отсутствие сбора данных.

## Проверка

Автоматические проверки выполнены на Windows в Chromium **156.0.8078.4** и Firefox **159.0.1**. `npm test` успешно завершился для обоих браузеров с фактической установкой расширения. В тестах нет ручного внедрения `shield.js` через средства автоматизации.

| Сценарий | Без расширения | С расширением | Проверено автоматически |
| --- | --- | --- | --- |
| Первое чтение API скриптом страницы | Нативные значения | `false / visible / true` | Оба браузера |
| Чтение выделенного абзаца | Непустая строка и диапазон | Пустая строка, диапазонов нет | Оба браузера |
| Выделение в input/textarea | Реальные границы | `0 / 0 / none` | Оба браузера |
| Настоящий ПКМ | `contextmenu` виден сайту | Обработчик сайта не вызывается | Оба браузера |
| Дополнительные события мыши, клавиш, выделения | Доставляются | Блокируются без отмены действия | Оба браузера, программная доставка событий |
| Обычная кнопка, ввод, фокус поля | Работают | Работают | Оба браузера |
| HTTP-iframe своего и другого origin | — | Первый скрипт видит подмену; выделение скрыто | Оба браузера |
| Настоящая фоновая вкладка | `hidden: true` в контрольной выборке | Все выборки `hidden: false`, `hasFocus: true`; событий видимости нет | Firefox |
| Строгая CSP без inline-скриптов | Демо работает | Демо работает | Оба браузера; в Chromium дополнительно проверяется отсутствие ошибок страницы |

Chromium проверяется в headless-режиме, в котором открытие соседней вкладки не меняет нативный `document.hidden`. Поэтому реальное скрытие вкладки отдельно подтверждено Firefox; событийные фильтры и значения API проверяются в обоих браузерах. Это ограничение среды проверки, а не доказательство поведения фоновой вкладки во всех браузерах.

Приёмка вручную: выполнить сценарий из `README.md` в видимых окнах обоих браузеров, отдельно проверить сворачивание окна, переход в другое приложение, стандартное меню, визуальное выделение и Ctrl+C/вставку. Сохранение содержимого системного буфера обмена автоматическими тестами не проверялось.

## Границы применимости

JavaScript-подмена не обеспечивает полной неотслеживаемости. Сайт разделяет контекст с расширением, может обнаружить заменённые методы, изменить их или получить чистые методы из нового iframe. В частности, ранний доступ к синхронно созданным пустым фреймам не перекрыт; у Firefox есть отдельное [ограничение внедрения в пустые iframe на document_start](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/content_scripts).

Фоновые таймеры, остановка `requestAnimationFrame`, lifecycle-события и приостановка вкладок управляются браузером. Сеть, workers, Idle Detection API и другие каналы этим решением не изолируются. Сайт продолжает получать обычный ввод, прокрутку и движение мыши и может делать косвенные выводы. Расширение также не ограничивает сбор cookies, IP-адреса, fingerprinting, камеры или микрофона.

Маскировка выделения нарушает приложения, которым требуется реальное положение курсора и диапазон выделения, особенно сложные редакторы. Для таких сайтов расширение нужно отключать с последующей перезагрузкой. Полная изоляция от намеренно противодействующей страницы потребовала бы изменений самого браузера и дополнительной модели доступа к данным, с существенным влиянием на совместимость веб-приложений.

Таким образом, практический результат закрывает прямые проверки из задания и демонстрирует механизм ограничения данных. Абсолютное утверждение «сайт никак не сможет определить уход пользователя» технически не обосновано и не является результатом этой работы.

## Дополнение: Android

По дополнительному условию подготовлена интеграция в существующий Firefox Android. Мобильная сборка находится в `dist/firefox-android`, её неподписанный XPI — `dist/activity-shield-firefox-android-unsigned.xpi`, отдельный комплект для сдачи — `dist/submission-android.zip`. 6 ноября 2026 года выполнен успешный интеграционный прогон на отдельном эмуляторе Android 16 / API 36, x86_64, с Firefox 159.0.1. В обычной видимой вкладке сравнивались контрольный режим и фактически загруженное расширение. Проверочная страница читала API собственным JavaScript и отправляла результаты на локальный HTTP-сервер; код защиты средствами теста в неё не внедрялся.

Контрольный режим показал реальное выделение текста и поля, событие `contextmenu` от настоящего долгого нажатия и изменение видимости при Home/возврате. С расширением чтение выделения давало пустые значения, событие контекстного меню и события смены видимости до обработчиков страницы не доходили, а API возвращали `false / visible / true`. Настоящее нажатие по кнопке и ввод `testingz` работали в обоих режимах. Статическая проверка мобильной сборки Mozilla `web-ext lint` завершилась без ошибок, предупреждений и замечаний; настольные тесты после расширения системы сборки также прошли.

Сохранённые результаты — `android/verification.json` и `android/verification.png`. Исходник проверки — `tests/android.test.mjs`; для запуска нужен подготовленный отдельный Android-эмулятор или тестовый телефон с включённой отладкой. Автоматический тест не заменяет ручную проверку системного копирования, маркеров выделения и поведения на физическом телефоне.

Мобильная версия сохраняет исходные ограничения JavaScript-подмены. В частности, Android может приостановить или завершить браузер в фоне: расширение не обеспечивает непрерывную активность и сетевые запросы. Обычные touch-события и длительность касаний остаются доступны сайту. Защита действует внутри Firefox; обычный Chrome на телефоне эту сборку не устанавливает.

При проверке установки на физическом телефоне обнаружено, что Firefox использует активный launcher-компонент `.AppMinimal`, тогда как `web-ext` по умолчанию пытается запустить `.App`. Проектная команда `android:run` исправлена: перед загрузкой она запрашивает актуальный компонент у Android Package Manager и передаёт его в `web-ext`. Добавлены проверки альтернативного значка, обычного launcher-компонента, Beta и ошибочного выбора устройства. На подключённом телефоне отдельно подтверждено определение `.AppMinimal` в режиме `--dry-run`, без повторного запуска браузера и установки. Этот диагностический результат не заменяет описанный выше полный прогон на эмуляторе или последующую ручную проверку установки на телефоне.

### Проверка исправления фокуса в 1.0.1

В Firefox уход приложения в фон может порождать также события активной кнопки или поля. Фильтрация только окна и документа оставляла канал через `blur`/`focus` и `focusout`/`focusin` этого элемента. В 1.0.1 такие переходы фильтруются отдельно. Используются сохранённые нативные [Document.hasFocus()](https://developer.mozilla.org/en-US/docs/Web/API/Document/hasFocus), `hidden`, `activeElement` и [FocusEvent.relatedTarget](https://developer.mozilla.org/en-US/docs/Web/API/FocusEvent/relatedTarget); переходы между полями активной страницы сохраняются.

Повторный полный прогон 1.0.1 на Android 16 / Firefox 159.0.1 прошёл. До Home фокусировалась кнопка; после возврата в защищённом режиме число фокусных событий не увеличилось. В контроле события приходили. Настоящие переходы фокуса между полем и кнопкой, обычный ввод, клики, выделение и контекстное меню также проверены. Машинный отчёт `android/verification.json` содержит версию, `focusHistory` и состояния `beforeHome`/`resumed`; в комплект включён новый снимок. Настольные проверки и Mozilla lint прошли. На физическом телефоне после обновления требуется повторить ручной сценарий Home/возврата; его успешность ещё не заявляется.
